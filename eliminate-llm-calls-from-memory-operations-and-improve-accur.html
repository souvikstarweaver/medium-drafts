Eliminate LLM Calls from Memory Operations and Improve Accuracy

Zero-Mem strips generative intermediaries and cuts latency 57.6 percent while raising F1 scores.

The Memory Tax: Why LLM Agents Pay for Recall

Every mainstream agent memory system works the same way. The agent accumulates history. The system calls an LLM to compress, summarize, or restructure that history into something retrievable. The agent calls the LLM again to retrieve from those generated abstractions. And then the agent calls the LLM a third time to answer the question.

The names change. MemoryBank, MemInsight, H-MEM, HippoRAG, AriGraph, Mem0, A-Mem, CompassMem. The pattern does not. Each system generates intermediate representations (summaries, reflections, hierarchical abstractions, graph indexes, linked memory records) and each system pays for them in recurring LLM tokens and latency Zero-Mem Paper, 2026.

The cost is not hidden. Generated abstractions make large histories accessible, but they turn memory management into a recurring generative workload. And when generated abstractions sit between the query and the raw history, omitted details, merged subjects, and blurred temporal updates weaken traceability to the original interaction Zero-Mem Paper, 2026. The assumption behind all of this is that LLM involvement in memory operations improves recall quality. That assumption, until now, went untested.

A new architecture called Zero-Mem tested it directly: can you eliminate LLM calls from every memory operation except the final question-answering step, and still recover (or improve) accuracy?

What Zero-Mem Does: A Four-Part Architecture

Zero-Mem's operating principle is specific. Memory construction, organization, routing, retrieval, evidence closure, and calibration all run without a single LLM call and consume zero LLM tokens Zero-Mem Paper, 2026. The LLM touches the pipeline once: at the end, to read the retrieved evidence and produce an answer.

Think of it like a library where no librarian writes summaries of the books. The books sit on shelves with their original text intact, indexed by author, subject, date, and cross-references. When you ask a question, the catalog system finds the right books and opens them to the right pages. A reader (the LLM) reads those pages and answers. The reader never builds the catalog, never writes summaries, never decides shelf placement.

The architecture has four components that replace every generative memory operation with deterministic, provenance-preserving alternatives.

How the System Stays Grounded: Provenance Without Generation

The first component is the Provenance-Preserving Token-Free Memory Substrate. Agent history is stored as a formal sequence of trace units, each containing the original text alongside source identifiers, session timestamps, boundary markers, and speaker metadata. Nothing is rewritten. Nothing is summarized Zero-Mem Paper, 2026.

From this raw substrate, Zero-Mem builds two non-generative views. The relational trace graph applies off-the-shelf named entity recognition (spaCy, not an LLM) to each trace unit, then constructs entity-to-context co-occurrence edges. Edge weights come from occurrence frequency, not inferred meaning. The temporal hierarchy organizes traces at four granularities: turns (single utterances), windows (short-range context blocks), episodes (semantically continuous groups of windows), and local spans (the immediate neighborhood around a candidate turn). Both views are indexed with BM25 for exact lexical matches (names, dates, numbers) and BGE-M3 dense embeddings for semantic similarity Zero-Mem Paper, 2026.

Retrieved evidence traces back to observed interactions, not to model-generated memory statements.

The Dual-View Trade-Off: Entity Relationships and Local Context

Two retrieval views exist because no single view captures both relationship structure and local context. The ablation study on HotpotQA (56K tokens, GPT-4o-mini) makes this concrete. The full model with both views scored 72.07 F1. The graph-only variant dropped to 62.50 F1. The hierarchy-only variant dropped further to 54.88 F1 Zero-Mem Paper, 2026.

That is a 17-point F1 gap between hierarchy-only and the full model, and a 9.5-point gap between graph-only and the full model. The graph connects information scattered across documents. The hierarchy preserves the local and multi-granular context needed to interpret those connections. Neither view alone is sufficient.

The graph-only variant's stronger performance is consistent with HotpotQA's emphasis on cross-document relational reasoning. For tasks requiring more local context, the hierarchy carries more weight. The two views are complementary, not redundant.

The Performance Claim: Accuracy Without the LLM Token Cost

Eliminating LLM calls from memory operations did not degrade quality. It improved it.

On the LoCoMo benchmark with GPT-4o-mini as the reader, Zero-Mem achieved the best average F1 and BLEU-1 scores, with improvements of 5.40 F1 points and 5.45 BLEU-1 points over GAM, the second-best baseline. With Qwen2.5-14B as the reader, improvements were 4.87 F1 points and 4.86 BLEU-1 points over GAM. With Qwen2.5-14B, Zero-Mem ranked first across every question type and every metric Zero-Mem Paper, 2026.

On HotpotQA, Zero-Mem achieved the highest F1 across all readers and all three context lengths, including the 448K-token setting (the longest and most challenging), with an average improvement of 5.52 F1 points over the strongest baseline Zero-Mem Paper, 2026.

The implication for anyone designing agent memory: the LLM calls your memory pipeline makes during construction, routing, and retrieval are not buying accuracy. A system that eliminates those calls and preserves raw provenance outperforms systems that use LLMs to generate memory intermediaries. The question to ask your own pipeline is direct: what is each LLM call in memory processing buying you, and can you measure it?

Why Incremental Reduction Is Not Enough: The LightMem Case

Two recent systems tried to close the efficiency gap by reducing, not eliminating, LLM involvement in memory operations. SimpleMem improved token efficiency through semantic structured compression and intent-aware retrieval planning. LightMem shifted several memory operations from large LLMs to specialized small language models and separated online retrieval from offline consolidation Zero-Mem Paper, 2026. Both still used LLM calls inside the memory pipeline. Neither targeted a design where final question answering is the only LLM-dependent stage.

The efficiency results expose the gap between partial reduction and full elimination. On LoCoMo with GPT-4o-mini, Zero-Mem achieved an F1 of 59.15 and BLEU-1 of 52.96, improving them by 10.0% and 11.5% over GAM. Zero-Mem consumed zero LLM tokens for memory operations. LightMem consumed more than 870,000 tokens. GAM took over 9,000 seconds of total processing time. Zero-Mem's total memory-operation latency was 334.77 seconds, with a per-query latency of 0.22 seconds. The latency reduction relative to LightMem (the fastest prior baseline) was 57.6% Zero-Mem Paper, 2026.

Token consumption and latency: Zero-Mem's zero-LLM-token approach outperforms LightMem and other baselines on both efficiency and accuracy.

The lesson is architectural. LightMem was designed to reduce memory-operation overhead. It used smaller, cheaper models for memory tasks. It still paid 870,000+ tokens for the privilege. Incremental reduction of LLM calls in memory operations is a local optimum. The optimization frontier is not "use a smaller model for memory tasks." The frontier is "remove the model from memory tasks." Zero-Mem's results establish that this frontier is reachable without sacrificing quality.

If your agent memory pipeline uses LLM calls for summarization, reflection generation, or graph construction, you are operating at the local optimum. The question is whether the architecture can be restructured so that only the final answer step touches an LLM.

The Honest Limits: Where the Paper Stops and Production Begins

Zero-token does not mean zero computation. Encoder inference for embeddings, named entity recognition, graph construction, retrieval scoring, and deterministic calibration all incur processing costs. Those costs are outside the LLM-token regime but are not free Zero-Mem Paper, 2026. A team evaluating this approach needs to measure encoder inference latency and NER pipeline throughput against their volume and SLA requirements.

The relational graph records observed co-occurrence and trace adjacency, not inferred semantic relationships. This is a deliberate design choice for provenance. It is also a structural limitation. Systems that generate richer relational triples (semantic relationships between entities, causal links, inferred attributes) capture information that co-occurrence graphs miss. For tasks where the reasoning requires understanding why two entities are related, not that they co-occur, the provenance-preserving graph may underperform.

The evaluation covers two benchmark families: LoCoMo (conversational, multi-session) and HotpotQA (multi-hop factual reasoning). Generalization to other agent task types, including tool use, multi-agent coordination, and real-time streaming, is not tested Zero-Mem Paper, 2026. An agent memory system operating in a tool-heavy environment (where the history includes API call chains, error traces, and state mutations) presents different retrieval challenges than conversational benchmarks.

The Choice: Architect Your Memory System for Provenance

The research question behind Zero-Mem is precise: can an agent memory system eliminate LLM calls from every operation outside final question answering, while retaining structured access beyond flat similarity retrieval Zero-Mem Paper, 2026? The answer, across two benchmark families, multiple readers, and context lengths up to 448K tokens, is yes.

For teams designing agent memory, this reframes the conversation. The question is no longer whether you can afford to remove LLM calls from memory operations. The question is whether you can justify keeping them. The evidence now shows that generated intermediaries (summaries, reflections, abstracted memory statements) cost tokens and latency without improving accuracy. They also break the provenance chain between the question and the raw evidence that answers it.

For regulated or auditable agent deployments, this distinction matters beyond performance. Eliminating generated intermediaries from the memory path means the system can trace every answer back to the original interaction, with no model-generated rewriting in between.

Conclusion

LLM involvement in agent memory operations is now a choice with empirical evidence on both sides. One path keeps generated abstractions in the pipeline, pays recurring token and latency costs, and accepts that the memory system rewrites history before retrieving from it. The other path preserves raw provenance, eliminates LLM calls from every memory operation except the final answer, and delivers equal or better accuracy at a fraction of the cost.

The decision is architectural and explicit. It belongs on the system design document, not buried inside a library default.
