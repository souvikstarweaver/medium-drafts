Your Model Is Not the Problem—Your Harness Is

When execution governance fails, even capable models submit broken work.

Why Agent Harness Governance Matters More Than Your Model

Your data-science agent fails on a benchmark task. The model produces malformed code, skips a required output file, and submits an incomplete result. The natural diagnosis: the model is not capable enough. Time to upgrade.

That diagnosis is wrong more often than most teams realize.

A new framework called DS-Lighting, built for data-science automation, tested this assumption head-on. The researchers paired a smaller model (Qwen) with a well-engineered harness and compared it to a larger model (GPT-5.5) paired with a standard orchestration layer (LangChain). The smaller model with the better harness won DS-Lighting, 2026. Not by a narrow margin on one task. Across a 947-task benchmark suite spanning reports, plots, code generation, and scientific computation.

The reason comes down to a concept the paper calls execution governance: the harness's ability to manage runtime state, validate artifacts before submission, recover from errors mid-task, and align evaluation feedback with the agent's next action. When the team removed execution governance from the harness, the macro-average score dropped from 0.5167 to 0.2714, the single largest collapse among three ablated components DS-Lighting, 2026. The failures that emerged were not capability gaps. They were system failures: state corruption, unhandled runtime errors, missing output files that no part of the system checked for.

This matters because most agent teams treat poor benchmark results as a signal to swap in a bigger model. The DS-Lighting results suggest the opposite order of operations: fix the infrastructure that wraps the model before spending tokens (and budget) on a larger one.

Prior agent systems made this diagnosis impossible. DS-Agent used a manual pipeline. AIDE optimized code iteratively. AutoKaggle embedded its own scaffolding. In every case, the harness was invisible, fused into the system, and unmeasurable DS-Lighting, 2026. You could not tell whether a bad result came from a weak model or a weak harness, because no one separated the two.

Harness-Bench, a benchmark released in 2025, was among the first to make the harness a primary axis of evaluation Harness-Bench, 2025. It recognized that existing agent benchmarks in other domains (web navigation, app testing, OS-level tasks) each addressed their own harness concerns, but none covered the joint problem of managing data context, code execution, and metric-based evaluation in a single workflow. DS-Lighting is the first framework to make the harness explicit and measurable for data-science workflows, and then stress-test each layer in isolation.

The Harness: Four Layers That Do More Than You Think

Think of a harness as the control room around a pilot. The pilot (the model) makes decisions. The control room (the harness) feeds the pilot the right instruments, executes the commands in a sandboxed environment, checks whether the landing gear is down before touchdown, and reports altitude in real time. A great pilot in a broken cockpit crashes. A decent pilot in a well-instrumented cockpit lands the plane.

DS-Lighting's harness has four layers, each with a distinct job DS-Lighting, 2026:

| Layer | Responsibility | What Breaks Without It | |---|---|---| | Data Layer | Extracts schemas, profiles datasets, converts raw task descriptions into a standardized task contract the agent can parse | Agent misreads input formats, ignores required columns, produces outputs against wrong specifications | | Workflow Layer | Defines available operators (tools the agent can call) and controls the sequence of actions | Agent has no structured action space, falls into open-ended generation loops | | Execution Layer | Runs each action in a sandbox, captures runtime state after every step, updates context for the next decision | Errors go undetected, state corrupts silently, agent submits broken artifacts | | Evaluation Layer | Returns structured feedback after each step (not only at the end), scores partial work against task metrics | Agent gets no mid-course correction signal, repeats the same mistake across iterations |

Task Input (raw question + data files) │ ▼ ┌─────────────────────┐ │ DATA LAYER │ DataAnalyzer: schema extraction, column profiling │ Task Handler │ Converts q_raw + data report → task contract └────────┬────────────┘ │ ▼ ┌─────────────────────┐ │ WORKFLOW LAYER │ Operator library (tools), Controller (manual or search) │ Action planning │ Selects which operators to run, in what order └────────┬────────────┘ │ ▼ ┌─────────────────────┐ │ EXECUTION LAYER │ Sandboxed runtime (Exec), state s_t → s_{t+1} │ State management │ Captures observations o_t, validates file outputs └────────┬────────────┘ │ ▼ ┌─────────────────────┐ │ EVALUATION LAYER │ EvalStep: structured mid-task feedback │ Scoring + repair │ G(x, τ_W, y): final task-level metric └─────────────────────┘

The four benchmarks in the test suite (DABench, DACode, MoSciBench, ScienceAgentBench) demand different artifact types: structured reports, statistical plots, executable code, NumPy arrays, and JSON outputs. Each benchmark stresses the harness differently. DABench requires precise tabular outputs where a single misread schema breaks the entire result. ScienceAgentBench requires reproducible scientific code where missing dependencies or unchecked runtime errors produce silent failures. The harness must handle all of these, not the model.

What Execution Governance Controls

When execution governance is removed from the harness, performance does not degrade. It collapses.

The sharpest drop appears on DABench, where the score falls from 0.8521 to 0.2724 DS-Lighting, 2026. DABench tasks require the agent to produce exact tabular outputs from structured data. Without execution governance, the agent cannot observe its own runtime state after each action. Code execution errors go unhandled. Output files are never checked before submission. Missing artifacts are never detected.

| Component Removed | Macro-Avg (Full) | Macro-Avg (Ablated) | Largest Benchmark Impact | Core Failure Mode | |---|---|---|---|---| | Data Grounding | 0.5167 | 0.3721 | DACode: 0.3709 → 0.2376 | Agent misreads input data, produces outputs against wrong specs | | Execution Governance | 0.5167 | 0.2714 | DABench: 0.8521 → 0.2724 | State corruption, unhandled errors, missing artifacts | | Evaluation Alignment | 0.5167 | 0.3971 | MoSciBench: 0.6477 → 0.3409 | No mid-task repair signal, repeated errors across iterations |

All three ablations hurt. Data grounding removal drops DACode from 0.3709 to 0.2376 and MoSciBench from 0.6477 to 0.3750. Evaluation alignment removal hits MoSciBench and ScienceAgentBench hard (ScienceAgentBench drops from 0.1961 to 0.0588 in both the data grounding and evaluation alignment ablations) DS-Lighting, 2026.

Execution governance produces the largest single drop because it is the runtime watchdog. Without it, agents enter feedback-blind loops. They generate code, the code fails, and no part of the system surfaces the failure. The agent moves to the next step with a corrupted state, compounds the error, and submits a broken artifact. The benchmark score reads as a capability failure. It is a system failure.

Why This Looks Like a Model Problem

The standard intuition makes sense on the surface: a more capable model should produce better code, reason more accurately, and handle edge cases that a smaller model cannot. If your agent scores poorly, upgrade the model.

The DS-Lighting results break this intuition. Qwen paired with DS-Lighting's four-layer harness outperforms GPT-5.5 paired with LangChain DS-Lighting, 2026. The gap is not explained by Qwen being a better model. It is explained by the harness catching errors that GPT-5.5 also makes but that LangChain does not surface or repair.

An LLM-as-judge analysis of the results shows the mechanism. DS-Lighting reduces failures tied to grounding mistakes, runtime state management, and evaluator-aligned repair. As these avoidable, system-level failures decrease, the remaining errors concentrate on intrinsic model limitations DS-Lighting, 2026. In other words: a good harness strips away the noise so you can see where the model is the bottleneck versus where the infrastructure is.

This is the attribution problem. In a system with a weak harness, every failure looks like a model failure. You cannot tell the difference between "the model cannot reason about this data type" and "the model produced the right code but the harness did not validate the output file." Both produce the same benchmark score: zero.

What You Should Do Differently

The practical implication is a change in diagnostic order. When an agent underperforms, the first audit should target the harness, not the model.

Three dimensions to check:

Data context legibility. Can your agent parse the data directory, schemas, column types, and output requirements without extra scaffolding you built by hand? DS-Lighting's Data Analyzer extracts compact dataset profiles and the Task Handler converts raw task descriptions into a standardized contract with structured fields DS-Lighting, 2026. If your agent receives a raw prompt and a file path with no schema information, it is operating blind. The data grounding ablation shows what happens: scores drop across every benchmark.

Runtime observation fidelity. Does your agent observe and log its own state after every action? Does it detect missing output files, failed code executions, and corrupt intermediate results before moving to the next step? The execution layer in DS-Lighting captures the observation o_t and updates the state s_{t+1} after each operator runs. Every file output is validated against expected schemas. Without this loop, agents submit broken work and never know it.

Evaluation feedback alignment. Does your agent receive structured, step-level feedback on partial work, or does it get a single pass/fail score at the end of the task? DS-Lighting's evaluation layer exposes task requirements not as final scores but as structured feedback during execution, giving the agent a repair signal at each step. The evaluation alignment ablation shows that removing this signal collapses ScienceAgentBench from 0.1961 to 0.0588. Without mid-task correction, agents repeat the same mistake in every iteration.

If all three layers are solid and performance is still poor, the model is the bottleneck. Upgrade then. Not before.

Where the Research Stops and Production Begins

The DS-Lighting results come from 947 tasks across four open academic benchmarks. The benchmarks are well-constructed and cover a range of data-science workflows (tabular analysis, code generation, scientific computation, plot generation). The results are reproducible.

They are also bounded. The paper states this: DS-Lighting "does not cover the full range of real-world industrial workflows, specifically private databases, streaming data, human-in-the-loop review, or domain-specific governance" DS-Lighting, 2026. Results depend on executable environments, library availability, and sandbox configuration. A team running agents against a proprietary medical claims database or a financial compliance pipeline faces constraints the benchmark suite does not test.

The vertical-agent literature suggests the finding may hold even more in those constrained environments. Domain-specific fine-tuned 8B-parameter models already outperform 175B general models on tasks like medical claims adjudication iCertGlobal Community, 2025. That pattern implies that system-level design (harness architecture combined with domain-specific tuning) dominates pure model scale in regulated verticals. But DS-Lighting has not tested this. The relative importance of harness governance in closed, governed production environments is an open question, and the answer is likely "even higher."

The Diagnostic Order

The default sequence in most agent teams is: agent fails, upgrade the model, re-run the benchmark, check the score. The DS-Lighting ablations make a case for a different sequence: agent fails, audit the harness (data context, execution observation, evaluation feedback), fix the weakest layer, re-run, and only then consider a model change.

The full harness produces a 0.5167 macro-average. Removing execution governance alone cuts that score nearly in half. No model upgrade closes a gap that large if the infrastructure around the model is the source of failure.

The question is not whether your model is good enough. The question is whether your model is getting a fair chance to be good enough.
